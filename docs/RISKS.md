# 위기 기록

숫자를 조용히 망가뜨릴 뻔한 것들. 무엇이 일어날 뻔했는지와 무엇이 잡아냈는지를 남긴다.
실험 수치는 `experiments.md`, 설계는 `SPEC.md`.

## 잡은 것

### 1. 경계에서 같은 `unix_ts` 가 두 구간에 쪼개질 뻔함
행 번호로 70/15/15 를 자르면 한 초에 몰린 줄이 train 과 val 로 나뉜다. BGL 은 초 해상도라
버스트 구간에서 실제로 일어난다. `split.snap()` 이 경계를 다음 타임스탬프로 민다.
**잡은 것**: done 조건의 "시간 경계 겹침 없음" 을 코드로 검증하려다 발견.

### 2. `kernel_mem` 이 train 에 99.88% 몰림 — 게이트가 한 줄 차이로 통과
218,075건 중 217,821건이 train. val 154 / test **100**. 중단 기준이 "100줄 미만" 이라
**정확히 100줄로 통과**했다. 규칙의 글자는 통과했지만 규칙이 막으려던 상황 그 자체였다.
90% 가 2005-06-12 ~ 06-14 이틀에 몰린 단일 장애 구간이라 비율 조정으로는 옮겨지지 않는다.
**잡은 것**: 게이트 통과만 믿지 않고 분포를 눈으로 봄. → 게이트 기준값을 재검토할 것.

### 3. test 를 줄여 점수를 올릴 뻔함
`kernel_mem` 표본이 얇으니 test 를 줄이자는 안이 나왔다. 계산해보니 normal 을 660,747 →
10,000 으로 덜어내면 **같은 모델의 F1 이 0.190 → 0.842**. 모델이 아니라 지운 행 수를 재는
숫자가 된다. 층화 축소는 비율이 유지되어 F1 이 전혀 안 변한다(어느 축소율에서도 0.190).
**결정**: test/val 은 그대로. 절대규칙 2 를 따른다.

### 4. `max_length` 를 32 로 줄일 뻔함 (알럿 클래스 절단)
단어 수 95 백분위가 10단어라 32 면 충분해 보였다. 실제 BERT 토큰으로 재니 `[NODE]`
`[NUM]` `[HEX]` 가 서브워드로 쪼개져 훨씬 길었고, **알럿이 정상보다 길었다**.
32 에서 무손실 비율: normal 95.23% / kernel_ops 77.38% / **app 53.40%**.
학습 시간 절반을 얻고 `app` 의 절반을 잃을 뻔했다. **64 로 확정.**
**잡은 것**: 단어 수 대신 실제 토크나이저로 클래스별 측정.

### 5. 완전 중복 제거(E6)를 기본 전략으로 쓸 뻔함
train 이 194.7배 중복이라 중복 제거가 최대 레버로 보였다. 클래스별 고유 템플릿을 세어보니
normal 16,902 / kernel_mem **9** / kernel_ops 24 / app 12.
완전 제거하면 `kernel_mem` 학습 예시가 9개, 정상 비율은 92.25% → **99.73%** 로 악화된다.
**결정**: `cap`(템플릿당 상한) 으로 대체. cap=2000 이면 10배 축소하면서 정상 비율 92.28% 유지.
dedup 은 E6 비교용으로만 남긴다.

### 6. torch 가 CPU 빌드 — GPU 가 놀고 있었음
`torch 2.13.0+cpu` 로 설치되어 RTX 4070 을 못 쓰고 있었다. 그대로 E2 를 돌렸으면
**전체 train 38.5시간/에폭, 5에폭에 8일**. cu126 으로 교체 후 약 1시간/에폭.
**잡은 것**: 학습 시간을 예측하다 `torch.cuda.is_available()` 확인.

### 7. `PROGRESS.md` 가 실제와 어긋나 3단계를 재실행할 뻔함
"데이터 복구 대기 — BGL.log 위치 확인 후 3단계 재실행" 이 남아 있었으나, 실제로는 원본
743,185,031 B 가 하드링크로 살아 있고 산출물 행 수도 전부 맞았다
(4,747,963 → holdout 271 → 빈 메시지 34,470 → 4,713,222).
**교훈**: 체크리스트보다 파일과 행 수를 먼저 본다.

**2026-08-29 재발.** "HF 모델 카드 남음" 이 남아 있어 모델 재학습이 필요하다고 판단했으나,
Hub 를 직접 보니 `illimax/bgl-log-triage-bert` 에 가중치(438MB)와 카드(6,693 B)가 이미
최신 상태로 올라가 있었다. `publish.py` 가 `runs/<exp_id>/checkpoint` 를 못 찾은 것은
로컬에 `runs/` 가 없을 때 나는 증상이지 미업로드의 증거가 아니다. 같은 교훈이 산출물이
원격에 있을 때도 적용된다 — **상태는 체크리스트가 아니라 실물에서 확인한다.**

### 8. cap 가설이 test 를 보고 나왔다 — test 오염

E1(none) 이 kernel_mem F1 0.4962 에 그친 뒤 `cap` 을 제안했는데, 그 근거가
**test 의 템플릿 구성을 열어본 것**이었다 ("train 은 TLB/스토리지인데 test 는
machine check 계열"). 최종 선택은 val 에서 했지만 **가설 자체가 test 에서 나왔다.**

정상 참작:
- `cap=2000` 은 점수가 아니라 클래스 비율 보존으로 정했다 (92.25% -> 92.28%).
  어떤 평가 점수에도 맞추지 않았다.
- val 이 독립적으로 같은 결론을 낸다. val 의 kernel_mem recall 이 0.6234 로 같은
  병목을 보였고 cap 적용 후 0.9805 다. test 를 안 봤어도 발견 가능했다.

그래도 **E1c 의 test 0.9316 은 편향 없는 추정치가 아니다.** 연구자 자유도가 오염됐다.

**이후 규칙**: 진단은 val/train 에서만 한다. test 는 확정된 설정을 한 번 확인하는
용도로만 연다. 모델 비교 판정은 미등장 템플릿 부분집합으로 한다.

### 9. 전체 macro F1 은 암기분이 섞여 있다

test 706,972행 = 기등장 템플릿 24.4% + 미등장 75.6%. 부분집합별 E1c macro F1 은
**기등장 0.9993 / 미등장 0.7451 / 전체 0.9316**. 기등장 구간은 사실상 암기다.

랜덤 분할 누수와는 다르다 — 시간순으로 잘랐고 로그가 반복되는 것은 운영 현실이다.
다만 **"새 장애 유형에 대한 성능" 을 묻는 답은 0.7451 이고 전체 점수가 아니다.**
보고할 때 세 숫자를 항상 같이 적는다. `ciod` 같은 단일 토큰 지름길은 확인 결과 없다
(train 의 `ciod` 줄 92,669개가 normal, 16,898개가 app).

## 아직 열려 있는 것

### A. val 이 test 의 대리 지표가 아니다  ← 가장 큰 미해결 위험
**2026-08-26 E2c 에서 현실화됐다. val 0.9941 → test 0.6829 (-0.3113).**
`tune_weights` 는 가중치 `[1,1,1,1]` 을 골랐다. val 이 이미 0.9941 이라 고칠 것을
못 본 것이지, 좌표상승이 틀린 게 아니다. **val 로는 이 붕괴를 볼 방법이 없다.**

미등장 템플릿 부분집합의 클래스별 표본 수가 val 과 test 에서 완전히 다르다:

| | val 미등장 (45.2%) | test 미등장 (75.6%) |
|---|---|---|
| normal | 292,391 (44.2%) | 497,690 (75.3%) |
| kernel_mem | **3** (1.9%) | 25 (25.0%) |
| kernel_ops | 27,453 (85.0%) | 5,259 (40.6%) |
| app | **0** (0.0%) | **31,641** (95.4%) |

val 은 쉽고 test 는 어려운 정도가 아니라 **구성 자체가 다르다.**

**"val 미등장 부분집합으로 체크포인트를 고르자"는 대안은 쓸 수 없다** — 4클래스 중
kernel_mem 이 3행, app 이 0행이다. 실제로 그 지표를 계산하면 E1c 0.4948 / E2c 0.6948 로
test 미등장 순위(E1c 0.7451 / E2c 0.4998)를 **거꾸로** 매긴다.

`train.early_stopping.metric: val_macro_f1` 은 test 에서 나쁜 모델을 고를 수 있다.
현재 이 프로젝트에는 **정직한 모델 선택 지표가 없다.** 미해결.

**2026-08-27 추가 — 대안으로 만든 inner-val 미등장 F1 도 실행 간 비교에는 못 쓴다.**

| | inner-val 미등장 (선택 지표) | test 미등장 (실제) |
|---|---|---|
| E2w (cap) | 0.6359 | **0.7330** |
| E2 (none) | **0.7255** | 0.5144 |

정의상 당연하다. inner-val 의 "미등장"은 **그 실행의 inner-train 기준**이라,
학습 입력이 다르면 두 지표가 서로 다른 행 집합을 잰다. E2 의 값이 큰 것은 모델이
좋아서가 아니라 미등장 집합이 쉬워졌기 때문이다.

**용도를 한 실행 안의 체크포인트 선택으로 좁힌다.** 그마저도 E2w 에서 에폭 1과 3을
0.0005 차로 갈랐는데 test 미등장은 0.2482 벌어졌다. 순서는 맞았지만 마진이 없다.

### B. `kernel_mem` test support 100건
F1 이 재현율이 아니라 오탐률로 결정된다. 정상 660,735건 중 오탐 66건(0.01%) 이하라야
F1 0.65. 부트스트랩상 macro F1 기여 불확실성은 ±0.010 이라 0.63 과 0.70 은 구분 가능하다.
`evaluate` 는 클래스별 support 와 오탐 건수를 반드시 같이 출력할 것.

### C. 임계값 보정은 val 에서만
argmax 는 정확도용 결정 규칙이라 macro F1 과 어긋난다. 클래스별 임계값 조정은 정당하고
`calibrate` 에 자리가 있다. **단 test 를 보며 맞추면 그 숫자는 일반화 추정치가 아니다.**
목표는 숫자가 아니라 운영 제약: 오탐 5건/일 = test 60.7일 기준 303건 = FPR 0.0459%.

### F. 무응답 규칙의 BGL 영향을 재보지 않았다  ← 2026-08-29 신규
`detect.outage` 와 `infer` 배선을 NASA 로만 검증했다. 이 머신에 `BGL.log` 도 학습된
모델도 없어 **BGL 알림 수(E1c val 4.8 / test 5.1건/일)가 움직이는지 실측하지 못했다.**

안 움직인다고 볼 근거는 두 가지뿐이고 둘 다 간접 근거다: (1) 규칙이 `직전 기준선 >= 20`
을 요구하는데 BGL 의 무로그 구간(90%)은 기준선이 0 에 붙어 있다, (2) "조용한 구간은
발화하지 않는다" 회귀 테스트. **로그 폭주가 갑자기 끊기는 구간에서는 발화할 수 있다.**
BGL.log 를 다시 받으면 `infer` 를 val/test 에 돌려 알림/일을 재측정할 것.

### G. 같은 트래픽 신호에 임계가 두 개
`judge()` 는 `infer.z_warning`(3.0) 으로 판정하고 출력 `flag` 는
`traffic.z_threshold`(3.0) 으로 만든다 (`src/infer.py:66,71` vs `traffic_view`).
지금은 값이 같아 증상이 없지만 한쪽만 바꾸면 `flag: "normal"` 인데 `reasons` 에는
"트래픽 급증"이 뜬다. 정본을 하나로 합칠 것.

### H. `configs/base.yaml` 의 `traffic.bucket` 은 아무도 읽지 않는다
실제 버킷 크기는 `infer.window` 다. 같은 값이 두 이름으로 있어 `traffic.bucket` 만
바꾸면 조용히 무시된다.

### I. `infer.run()` 의 구간별 상위 샘플 추출이 매번 전체 스캔이다
`part = df[df["bucket"] == ts]` 를 구간마다 돈다. 구간 수 × 전체 행 수라 BGL test
719,665행에서 무겁다. `groupby("bucket")` 한 번이면 된다.

### E. 학습된 모델의 신뢰도가 포화돼 `unknown` 이 작동하지 않는다
E2c 의 오분류 20,752건 **전부**가 최대 softmax 확률 0.99997 이상이다.
`infer.conf_threshold` 를 0.9999 까지 올려도 걸러지는 행이 0 이라, SPEC 5-5 의
미분류 처리와 `calibrate` 가 E2c 위에서는 아무 일도 하지 못한다.
16,945종을 19.6배 중복된 332,955행으로 5에폭 돌린 결과다 (train loss 0.0002).
E1c 는 오분류 최소 신뢰도 0.537 로 여유가 있다 — 포화는 BERT 쪽 문제다.
`holdout_rare` 271건이 `unknown` 으로 나오는지 확인하는 검증도 이 상태로는 통과할 수 없다.
