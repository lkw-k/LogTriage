# 위기 기록

숫자를 조용히 망가뜨릴 뻔한 것들. 무엇이 일어날 뻔했는지와 무엇이 잡아냈는지를 남긴다.
실험 수치는 `experiments.md`, 설계는 `SPEC.md`.

## 잡은 것

### 1. 경계에서 같은 `unix_ts` 가 두 구간에 쪼개질 뻔함
행 번호로 70/15/15 를 자르면 한 초에 몰린 줄이 train 과 val 로 나뉜다. BGL 은 초 해상도라
버스트 구간에서 실제로 일어난다. `split.snap()` 이 경계를 다음 타임스탬프로 민다.
**잡은 것**: done 조건의 "시간 경계 겹침 없음" 을 코드로 검증하려다 발견.

### 2. `kernel_mem` 이 train 에 99.88% 몰림 — 게이트가 한 줄 차이로 통과
218,075건 중 217,821건이 train. val 154 / test **100**. 중단 기준이 "100줄 미만" 이라
**정확히 100줄로 통과**했다. 규칙의 글자는 통과했지만 규칙이 막으려던 상황 그 자체였다.
90% 가 2005-06-12 ~ 06-14 이틀에 몰린 단일 장애 구간이라 비율 조정으로는 옮겨지지 않는다.
**잡은 것**: 게이트 통과만 믿지 않고 분포를 눈으로 봄. → 게이트 기준값을 재검토할 것.

### 3. test 를 줄여 점수를 올릴 뻔함
`kernel_mem` 표본이 얇으니 test 를 줄이자는 안이 나왔다. 계산해보니 normal 을 660,747 →
10,000 으로 덜어내면 **같은 모델의 F1 이 0.190 → 0.842**. 모델이 아니라 지운 행 수를 재는
숫자가 된다. 층화 축소는 비율이 유지되어 F1 이 전혀 안 변한다(어느 축소율에서도 0.190).
**결정**: test/val 은 그대로. 절대규칙 2 를 따른다.

### 4. `max_length` 를 32 로 줄일 뻔함 (알럿 클래스 절단)
단어 수 95 백분위가 10단어라 32 면 충분해 보였다. 실제 BERT 토큰으로 재니 `[NODE]`
`[NUM]` `[HEX]` 가 서브워드로 쪼개져 훨씬 길었고, **알럿이 정상보다 길었다**.
32 에서 무손실 비율: normal 95.23% / kernel_ops 77.38% / **app 53.40%**.
학습 시간 절반을 얻고 `app` 의 절반을 잃을 뻔했다. **64 로 확정.**
**잡은 것**: 단어 수 대신 실제 토크나이저로 클래스별 측정.

### 5. 완전 중복 제거(E6)를 기본 전략으로 쓸 뻔함
train 이 194.7배 중복이라 중복 제거가 최대 레버로 보였다. 클래스별 고유 템플릿을 세어보니
normal 16,902 / kernel_mem **9** / kernel_ops 24 / app 12.
완전 제거하면 `kernel_mem` 학습 예시가 9개, 정상 비율은 92.25% → **99.73%** 로 악화된다.
**결정**: `cap`(템플릿당 상한) 으로 대체. cap=2000 이면 10배 축소하면서 정상 비율 92.28% 유지.
dedup 은 E6 비교용으로만 남긴다.

### 6. torch 가 CPU 빌드 — GPU 가 놀고 있었음
`torch 2.13.0+cpu` 로 설치되어 RTX 4070 을 못 쓰고 있었다. 그대로 E2 를 돌렸으면
**전체 train 38.5시간/에폭, 5에폭에 8일**. cu126 으로 교체 후 약 1시간/에폭.
**잡은 것**: 학습 시간을 예측하다 `torch.cuda.is_available()` 확인.

### 7. `PROGRESS.md` 가 실제와 어긋나 3단계를 재실행할 뻔함
"데이터 복구 대기 — BGL.log 위치 확인 후 3단계 재실행" 이 남아 있었으나, 실제로는 원본
743,185,031 B 가 하드링크로 살아 있고 산출물 행 수도 전부 맞았다
(4,747,963 → holdout 271 → 빈 메시지 34,470 → 4,713,222).
**교훈**: 체크리스트보다 파일과 행 수를 먼저 본다.

## 아직 열려 있는 것

### A. val 이 test 의 대리 지표가 아니다  ← 가장 큰 미해결 위험
test 행 기준 미등장 템플릿 비율은 normal 75.3% / **app 95.4%** / kernel_ops 40.6% 인데,
val 의 `app` 은 **0.0%** (4종 전부 train 에 있음). val 은 쉽고 test 는 어렵다.
`train.early_stopping.metric: val_macro_f1` 으로 베스트 체크포인트를 고르면 test 에서
나쁜 모델을 고를 수 있다. **E2 에서 체크포인트 선택 근거를 다시 볼 것.**

### B. `kernel_mem` test support 100건
F1 이 재현율이 아니라 오탐률로 결정된다. 정상 660,735건 중 오탐 66건(0.01%) 이하라야
F1 0.65. 부트스트랩상 macro F1 기여 불확실성은 ±0.010 이라 0.63 과 0.70 은 구분 가능하다.
`evaluate` 는 클래스별 support 와 오탐 건수를 반드시 같이 출력할 것.

### C. 임계값 보정은 val 에서만
argmax 는 정확도용 결정 규칙이라 macro F1 과 어긋난다. 클래스별 임계값 조정은 정당하고
`calibrate` 에 자리가 있다. **단 test 를 보며 맞추면 그 숫자는 일반화 추정치가 아니다.**
목표는 숫자가 아니라 운영 제약: 오탐 5건/일 = test 60.7일 기준 303건 = FPR 0.0459%.
